Infinigen × Mitsuba 연동 계획 — 러프 스케치

Infinigen이 무한히 생성하는 RGB 기반 3D 장면에 측정 pBRDF를 링킹하고 Mitsuba로 렌더하면, 편광·초분광 3D 장면을 무한히 만들 수 있다는 가설.

Geometric Diversity(Infinigen) × Optical Fidelity(HPBRDF + Mitsuba) → 무한 Polarimetric / Hyperspectral 3D 데이터셋

핵심 아이디어

Infinigen은 형상과 배치의 무한 다양성을 준다. Mitsuba + 측정 pBRDF는 센서가 실제로 보는 방식(편광·NIR·초분광)을 물리적으로 정확하게 렌더한다. 두 개를 이어붙이면, 기존 합성 데이터셋이 갖지 못한 조합이 생긴다.

Infinigen이 주는 것
기하 다양성

182개 생성기, 1070 DOF, 절차적 배치. 장면 하나마다 형상·재질·조명이 모두 다르다.

HPBRDF가 주는 것
측정 광학 재질

실제 표면을 분광·편광 측정한 pBRDF. 시뮬레이션이 아니라 실측값이므로 센서 응답이 현실적이다.

Mitsuba가 주는 것
물리 기반 렌더

Stokes 벡터 편광, 분광 variant, Mueller 행렬 BSDF. 측정 pBRDF를 그대로 플러그인으로 쓸 수 있다.

한 줄 주장: 장면 구조는 Infinigen이 무한 생성하고, 광학 재질은 측정값으로 교체하면 — 기존 합성 데이터셋에는 없던 편광·초분광 ground truth가 있는 실내 3D 데이터셋을 대량 생산할 수 있다.

연동 파이프라인 개요

Infinigen 장면 생성 (procedural geometry + 기본 PBR 재질) │ ▼ 물체 분류 / 재질 매핑 (Infinigen 재질 태그 → HPBRDF 카테고리 룩업) 예) 금속 → steel_304, 유리 → borosilicate, 플라스틱 → abs_white ... │ ▼ Mitsuba 씬 딕셔너리 빌드 (mitsuba_builder: geometry + measured_polarized_rgb BSDF 링크) │ ▼ Mitsuba 멀티모달 렌더 cuda_ad_spectral_polarized variant → RGB / Depth / Normal / Stokes(S0·S1·S2·S3) / 분광 채널별 radiance │ ▼ OpticalNav 데이터셋 번들 (viewpoint graph + observation manifest + GT labels)

재질 매핑 전략

Infinigen의 기본 재질은 principled BSDF (base_color, roughness, metallic). 이것을 측정 pBRDF로 교체할 때, 두 가지 레벨로 나눌 수 있다:

레벨 A — 재질 카테고리 매핑
물체 유형 → 대표 pBRDF

금속 물체 → 대표 금속 pBRDF, 플라스틱 → 대표 플라스틱 pBRDF.
구현 난이도 낮음. 재질 내 공간적 변화 없음.

현재 가능
레벨 B — Spatially Varying BRDF
RGB texture → 위치별 pBRDF 보간

Infinigen의 RGB 텍스처 맵을 쓰면서 위치마다 다른 pBRDF를 적용. 나무결, 금속 스크래치, 도장 불균일 등 표현 가능.

미완성

알려진 문제점 3가지

아이디어는 성립하지만, 실제 파이프라인을 돌리기 전에 해결해야 할 병목이 명확히 있다.

① HPBRDF 가짓수가 ~30종으로 부족하다

현재 data/hpbrdf_2025/에 있는 측정 pBRDF는 약 30종. 실내 장면 하나에는 수십~수백 종류의 표면이 등장한다 (목재, 직물, 세라믹, 플라스틱, 유리, 금속, 가죽, 페인트, 도배지…).

  • 30종으로 전체 장면을 커버하면, 사실상 동일한 광학 재질이 여러 다른 물체에 반복 할당된다.
  • 데이터셋 다양성 논문 심사 기준에서 "재질 다양성이 없다"는 약점이 된다.
  • 편광/NIR 관측에서 가장 큰 차이를 만드는 것은 재질 차이인데, 이게 30종이면 클래스 분리가 쉬워져 오히려 현실과 동떨어진 "쉬운 데이터셋"이 될 수 있다.
현실적 대응: 단기적으로는 "재질이 다양하지 않음을 명시적 한계로 인정"하고, 카테고리 다양성(금속/플라스틱/유리/직물 등 대분류) 위주로 데이터셋을 설계. 중기적으로 KAIST pBRDF 2020 + HPBRDF 2025 + 공개 측정 데이터(MERL BRDF 등) 합산해서 종류를 늘리는 방향.
② RGB texture map 기반 Spatially Varying BRDF 렌더링이 아직 완성 안 됨

Infinigen 장면의 핵심 시각적 품질은 texture map에서 온다 (나무결, 대리석 패턴, 패브릭 직조 등). 단순히 단일 pBRDF를 물체 전체에 적용하면 이 공간적 변화가 사라진다.

  • Spatially Varying BRDF(SV-BRDF)는 위치 (u, v)마다 다른 BSDF 파라미터를 써야 한다.
  • 측정 pBRDF를 SV-BRDF로 쓰려면 Mitsuba 플러그인 레벨에서 texture → pBRDF 파라미터 보간 로직이 필요하다.
  • 현재 measured_polarized_rgb 플러그인은 단일 균일 재질만 지원 (data_path 고정).
  • 가장 현실적인 경로: Albedo map을 pBRDF 색상 스케일로 곱하기 — 정확한 SV-BRDF는 아니지만 시각적으로는 자연스럽고, 편광 패턴은 pBRDF에서, 색상 변화는 texture에서 나눠 갖는 근사.
현재 상태: 미구현. 구현 난이도는 중간 (플러그인 C++ 수정 또는 Python 래퍼에서 pre-compose). 이 없이도 레벨 A 매핑은 가능하지만, 결과물이 "텍스처 없는 단색 물체" 처럼 보일 수 있다.
③ 전체 파이프라인 시간 비용이 크다

각 단계마다 상당한 시간이 필요하고, 이 중 검수 단계가 자동화가 어렵다는 점이 특히 문제다.

분광+편광 variant, SPP 수백~수천. 실시간 불가. GPU당 분~수십분/frame.
  • 실시간 피드백 루프 없음: 장면을 생성하고 → 재질 교체하고 → 렌더해보기까지 반나절~하루 단위. 파라미터 실험이 느리다.
  • 검수 병목: Infinigen 씬이 항상 좋은 NavEpisode 후보를 만드는 것은 아니다. 통로가 없거나, 조명이 없거나, 씬이 너무 넓거나. 이 검수를 자동화하는 기준(traversability, lighting sufficiency, scale)을 정의해야 한다.
  • 비용 규모: OpticalNav 데이터셋에 장면 10개 × viewpoint 100개 × heading 4방향 = 4000 프레임. 프레임당 5분이면 333시간 = GPU 10개로 33시간.
구조적 선택: PBR 렌더링인 이상 실시간은 포기. 대신 배치 재렌더 인프라(rerender_optical_nav_grid.py)를 강화해서 씬 교체 → 재렌더를 최소 조작으로 돌리는 방향이 현실적.
