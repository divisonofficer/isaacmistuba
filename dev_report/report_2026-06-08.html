오늘 기준으로 editor에서 배치한 공유오피스 오브젝트가 Mitsuba 렌더 결과에 보이는 흐름은 살아났다. 특히 MooreLane 출신 chair/table/storage mesh는 fallback box가 아니라 실제 mesh로 도달하는 케이스가 확인되었다. 다만 시각적으로는 텍스처가 빠진 검은 물체처럼 보이는 문제가 남아 있으며, 이는 geometry보다 material binding 쪽 문제로 좁혀졌다.

Hot Camera Preview

문제정리된 방향
preview render를 하려면 graph/grid viewpoint를 만들어야 해서 빠른 시점 확인이 어려웠다. 임시 preview camera를 graph에 저장하지 않고, 3D view의 click + drag pose로 custom preview sweep을 보낸다.
Preview 탭과 "preview from here" 기능이 따로 놀았다. "preview from here"가 Preview 탭의 hot camera 상태로 이어지도록 기능 흐름을 합치는 방향으로 정리했다.
preview camera가 하나뿐이라 새 위치를 찍으면 이전 history가 사라졌다. preview camera를 단일 mutable state가 아니라 preview object/job history로 남기는 모델이 필요하다는 결론을 냈다.
프러스텀이 panorama render plane처럼 보여 실제 rig FOV와 맞지 않았다. active rig sensor의 intrinsics, FOV, resolution aspect로 frustum을 계산해야 한다.
숨겨진 heading plane이 클릭되는 문제가 있었다. raycast 후보에서 visible mesh/group만 선택되도록 click filter를 강화하는 방향으로 정리했다.

fallback box 크기가 실제 DTC object보다 과하게 컸다. asset-native bounds 또는 metadata proxy size가 fallback geometry에 일관되게 반영되지 않는 문제가 남아 있다.

Material / Texture 진단

현재 가장 큰 품질 병목은 mesh가 아니라 material이다. office object가 실제 텍스처를 쓰는 것이 아니라, coarse taxonomy가 고른 measured BSDF 하나로 통째로 렌더되는 경향이 강하다. 그래서 렌더 결과가 검은색 플라스틱/당구공/PEEK처럼 어둡고 단조롭게 보인다.
원인세부 내용
Coarse material mapping desk/table/storage는 pbrdf_2020:peek, chair는 hpbrdf_2025:black_rough_plastic, electronics는 pbrdf_2020:black_billiard처럼 하드코딩되어 있다.
Source texture 미반영 MooreLane OBJ/MTL에는 base color texture가 있지만 현재 생성 XML/materialization audit에는 source material/texture metadata가 비어 있었다.
GLB material loss DTC GLB는 OBJ geometry cache로 변환되면서 내부 PBR material/texture가 cache metadata와 BSDF 생성 경로에 보존되지 않는다.
hpBRDF channel behavior scene render에서 channel-split hpBRDF가 RGB composite이 아니라 특정 wavelength placeholder처럼 쓰일 수 있다.
Dataset overlap white_billiard처럼 pBRDF/hpBRDF 이름이 겹치면 의도치 않게 hpBRDF channel path로 대체되는 케이스가 있다.

결론적으로 현재 렌더가 어두운 것은 조명만의 문제가 아니다. 오브젝트에 office-domain material이 붙은 것이 아니라 제한된 measured material library에서 가까운 이름의 어두운 재질이 object-level override로 들어간 것이 더 큰 원인이다.

Material Policy 개선 계획 · 발표용 요약

Texture는 "공간적으로 어디가 어떤 색/패턴인가"를 말하고, BRDF는 "그 재질이 빛을 어떤 각도, 파장, 편광 상태로 반사/투과하는가"를 말한다. 두 정보는 같지 않으므로 하나로 덮어쓰면 office scene 품질이 망가진다.

현재 문제는 hpBRDF/pBRDF를 쓰는 것 자체가 아니라, object 하나에 measured BRDF 하나를 통째로 꽂으면서 USD/GLB/OBJ가 갖고 있던 native texture와 material slot 정보를 잃는 데 있다. v1에서는 단일 material mode로 해결하려 하지 않고, RGB appearance와 optical cue를 분리해서 다룬다.

Editor mesh preview · XML-native + cache pipeline

그동안 editor가 보던 mesh와 Mitsuba가 실제로 렌더한 mesh가 서로 다른 경로를 사용하고 있었다. editor는 USD prim cache를 보고, render는 render_scene.xml + mesh_cache/*.obj를 보는 이중 구조여서 "에디터에선 정상으로 보이는데 렌더에선 안 보인다" 또는 그 반대 케이스가 자주 발생했다. 오후 작업으로 editor가 sync 결과인 xml_scene_index.json을 source of truth로 삼고, mesh_cache OBJ를 그대로 가져와 표시하도록 흐름을 일원화했다.

레이어변경 내용
Frontend cache apps/webui/src/lib/objMeshCache.ts 신규 — Memory LRU (96) + IndexedDB (14일 TTL) 두 계층. OBJLoader.parse 결과를 BufferGeometry로 직렬화/역직렬화. primMeshCache와 별도 DB 이름으로 충돌 방지.
Burst protection 한 scene당 100+ OBJ가 동시 fetch되면서 데몬 health가 timeout. semaphore(4 in-flight) + Content-Length 가드(8 MB)로 큰 mesh는 placeholder로 처리하도록 했다. 결과적으로 트래픽 1.7 GB → 수백 MB 수준.
TCP drain BaseHTTPRequestHandler.wfile이 unbuffered(wbufsize=0)인데도 다중 MB 응답에서 ERR_CONTENT_LENGTH_MISMATCH가 반복 발생. Connection: close + socket.sendall + shutdown(SHUT_WR)로 graceful half-close하니 해결되었다.
GLB OBJ mirror GLB → trimesh → glb_obj_cache/<digest>/mesh.obj는 그대로 두되, scene별 mesh_cache/glb_<digest>.obj로 hardlink/copy해서 editor가 basename 한 가지 endpoint(/scenes/<id>/mesh-cache/<filename>)로 다 받을 수 있게 했다.
OBJ writer v3 이전 writer는 bottom-at-y=0만 적용(Y 정규화). Main Couch는 prim pivot이 한쪽 끝이라 vertex가 z ∈ [-15.62, 0]으로 export되어 placement translate와 어긋났다. v3에서 x/z도 bbox center로 평행이동. 기존 캐시는 digest mismatch로 자동 invalidate.
Floor fallback traversable region이 없을 때 _compute_floor_slabs가 하드코딩 20×20을 쓰던 fallback을 settings.map_w/map_h 우선으로 바꿔서 editor 그리드와 floor 크기가 일치.
Staging XML 경로 render 단계의 .staged_mitsuba/base/<hash>.xml이 repo-relative OBJ 경로를 다시 쓰는 문제로 Mitsuba 로더가 파일을 못 찾는 회귀가 있었다. staged XML의 <string name="filename">을 absolute path로 작성하도록 수정.
결과적으로 editor에서 본 mesh와 Mitsuba 렌더에 들어가는 mesh가 같은 OBJ 파일이 되었다. Main Couch / Blue Dumbbell처럼 "보이지 않거나 위치가 어긋나던" 케이스들이 대부분 해소.

Episode path-only sweep · episode_nodes

VLN dataset을 만들려면 모든 viewpoint × heading을 sweep해야 했는데, scene이 커지면 수백 노드 × 4 heading × 멀티 모달이라 시간이 비현실적이었다. 사용자는 우선 만든 episode가 지나가는 path_nodes 위주로만 렌더하기를 원했다.

지점구현
Backend build_sweep_render_requests(node_ids=...)와 _handle_opticalnav_graph_sweep이 이미 node_ids 필터를 받을 수 있게 만들어져 있어서 백엔드 무수정으로 진행.
Frontend render mode renderMode 값에 'episode_nodes' 추가. isGraphSweepRenderMode 헬퍼로 gate를 통일 (activeBatch, refreshBatch, WS subscribe, BottomPanel grid 모두 같은 경로).
Submission renderEpisodes('episode_nodes')가 body에 node_ids: selectedEpisode.path_nodes + source_episode_id 동봉.
UI · Sensors 탭 기존 "Graph Sweep · all viewpoints" 옆에 "Graph Sweep · episode path (N × M jobs)" 추가. episode 비선택 / trajectory-only면 disabled + 툴팁.
UI · Paths 탭 Sensors 탭까지 가지 않아도 episode 선택 직후 "▶ Render episode path" 버튼이 같은 자리에 뜨도록 추가.

효과는 단순하다. 70 노드짜리 scene에서 path 12개만 렌더하면 48 jobs (12 × 4 heading) 수준으로 끝난다. VLN evaluation을 시도하는 데 필요한 최소 데이터만 빠르게 만들 수 있게 되었다.

Job status WebSocket 전환

DevTools Network에서 9분 동안 ~3,000 requests / 302 MB transferred가 관측되고 데몬 health 체크가 간헐 timeout. 주범은 datasets/+page.svelte의 _refreshBatchLogs()와 fetchRenderBatch()가 4초마다 active batch 수 × 2개의 HTTP를 병렬 발사하던 것. 이미 백엔드에 /api/ws/job-status가 있어 같은 데이터를 푸시 중이었으므로, datasets 페이지를 그쪽으로 옮겼다.

모듈역할
lib/stores/jobStatusWs.ts (신규) 싱글톤 WS 클라이언트 + subscriber set + 자동 재연결(3s) + _last replay. 여러 페이지가 같은 connection을 공유.
applyJobStatusUpdates (배치 helper) WS의 flat job record ({job_id, status: "succeeded", progress_stage, ...})를 batch의 nested status object 형태로 reshape하면서 graph_id/node_id/heading_id 등 batch 메타데이터를 보존.
logTailsToBatchEntries WS의 log_tails: {job_id: [lines...]}을 batch의 {job_id, line}[] 형태로 변환, 현재 batch에 속한 job_id만 필터.
startBatchPolling graph_sweep / episode_nodes면 setInterval 폐지하고 WS subscribe. 첫 frame이 batch metadata fetch 이전에 도착해도 드롭되지 않도록 async + 750ms retry로 race 해소.
Fallback WS frame에서 batch의 succeeded job 발견 시 refreshBatch()를 한 번 더 호출하는 belt-and-suspenders. 실제 completion event 시점에만 발생해서 4초 폴링보다 가볍다.
디버깅용 window.__jobStatusDebug를 임시로 노출해 WS 매 프레임 단위로 matched_in_batch / succeeded_in_batch_frame / batch_completed를 확인할 수 있게 했다. 안정화되면 제거 예정.

부분 sweep 결과만 export

위 흐름의 결과로 사용자는 episode path 일부만 점진적으로 렌더하는 사용 패턴을 갖게 되었다. 그런데 기존 POST /opticalnav/<project>/export는 모든 episode를 무조건 포함해서, observation_bundle_ref가 비어 있는 episode까지 zip에 들어가 외부 VLN evaluator가 missing observation으로 실패하는 문제가 있었다.

레이어변경 내용
Backend (exporters/custom_json.py) is_episode_complete(episode, dataset_root) helper — 모든 timestep의 observation_bundle_ref가 디스크에 실제로 있어야 True. build_dataset_index / write_dataset_index / write_split_files / export_dataset_zip에 episode_ids와 only_completed 인자 추가. dataset.json에 total_episode_count_on_disk / skipped_episode_count / filter 메타 기록.
Daemon endpoint POST /export payload에 episode_ids, only_completed 수용 후 export 함수들에 그대로 전달. 응답에 kept/skipped 카운트 동봉.
Frontend (ExportPanel / RailExportTab) "Only rendered episodes" 체크박스(디폴트 ON) + "Exporting X of Y episodes" hint. export 직후 "kept N · skipped M · on disk K" 요약 표시.
Zip scope zip 자체는 dataset_root 전체를 그대로 보관. 외부 reader는 dataset.json / splits/*.json만 따라가면 자동으로 완성된 episode subset만 본다. 구현 단순 + 추후 zip slim down은 후속 작업. 
$ python smoke
is_complete(a):  True
is_complete(b):  False
all:             2 episodes, skipped 0

이번 라운드의 종착점은 사실상 "부분 sweep으로도 dataset이 유효하게 export된다"는 것이다. episode_nodes 모드로 일부 path만 렌더해도 그것만 모아 외부 VLN evaluator에 넘길 수 있는 파이프라인이 통째로 닫혔다.

남은 이슈

우선순위이슈판단
1 3모드 material policy를 구현해야 한다: RGB native texture, NIR/Polar measured BRDF, 중기 Hybrid. office 씬 품질의 핵심이다. OBJ/GLB native texture를 무시하면 계속 검게 보이고, measured BRDF를 버리면 optical cue가 약해진다.
2 preview camera history를 editor object처럼 관리해야 한다. hot camera가 하나의 mutable state이면 이전 렌더 위치와 결과 추적성이 사라진다.

5 fallback box 크기와 mesh bounds를 asset-native scale 기준으로 통일해야 한다. DTC object가 작게 의도된 경우 fallback도 작아야 한다.

7 window.__jobStatusDebug 임시 노출과 belt-and-suspenders refreshBatch() 호출 제거. WS-only 경로가 안정화되면 둘 다 떼어내야 한다.

짧은 평가

6월 8일의 성과는 렌더 시스템이 눈에 보이는 단계로 들어왔다는 점이다. editor, camera rig, render daemon, Mitsuba output 사이의 데이터 흐름이 실제 office scene에서 맞물리기 시작했다. 남은 문제들은 대부분 "렌더가 안 된다"가 아니라 "정확히 어떤 geometry/material/source를 렌더했는지"의 문제로 바뀌었다.

오후에는 그 흐름을 사용자가 실제로 돌릴 수 있는 형태까지 닫았다. editor가 렌더 mesh를 그대로 보여주고(xml_scene_index + objMeshCache), episode_nodes 모드로 path만 우선 렌더하고, WS로 진행 상태를 받고, 완성된 episode만 골라 export — 이 한 줄짜리 사이클이 처음으로 끝까지 흘러간다.

다음 단계는 두 갈래로 갈린다. 하나는 material policy를 정교하게 만드는 것이다 — asset-native texture + measured BRDF library 조합. 다른 하나는 VLN 외부 호환이다 — R2R / VLN-CE 같은 표준 포맷 exporter, observation bundle layout 명세, 그리고 외부 agent rollout adapter. 데이터셋이 닫혔으니 이제 평가 루프를 열 차례다.
