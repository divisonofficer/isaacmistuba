XML-native Preview 전략 평가

핵심 방향은 명확하다. 렌더 진실은 XML에 있고, 에디터는 그 XML이 실제로 참조하는 mesh/material/light/sensor를 보여줘야 한다. 따라서 현재 작업의 중심은 authoring map을 예쁘게 보여주는 것이 아니라, render_scene.xml, render_scene_materialization.json, xml_scene_index.json가 말하는 실제 렌더 입력을 에디터에 반영하는 것이다.

XML-native preview 기본값에 대한 판단

XML-native preview는 방향이 맞지만, 아직 default on으로 켜기에는 이르다. 최소한 아래 acceptance를 통과하기 전까지는 opt-in toggle로 유지하는 것이 안전하다.

Acceptance통과 기준
대표 sceneoffice_lobby_001, moorelane_kitchen_001에서 실제 mesh가 표시된다.
Fallback 표현GLB fallback object는 cube로 보이되 warning/reason이 같이 표시된다.
실패 내성OBJ fetch 실패가 전체 editor crash로 이어지지 않는다.
편집성selected object inspector와 transform gizmo가 XML-loaded mesh에서도 정상 동작한다.
성능대형 scene에서 mesh_cache OBJ preview가 interaction을 망치지 않는다.

지금 바로 해야 할 순서

  1. PR2.5a: <MapEditor3D>에 xmlSceneIndex, xmlNativePreviewEnabled, opticalNavProjectId, opticalNavSceneId binding을 복구한다.
  2. 화면 검증: XML-native preview toggle ON 상태에서 mesh-cache endpoint 요청이 발생하는지, chair/table이 box가 아니라 mesh로 보이는지 확인한다.
  3. Stale index 검증: xml_scene_index.xml_mtime_ns와 render_scene.xml stat mtime이 다르면 XML index may be stale. Re-sync render scene. 경고를 띄운다.
  4. Material audit: missing material prim, black basecolor suspected, opacity < 1, texture connection unresolved list를 먼저 모은다.
  5. Readiness 분리: UI에 Render: ready · 102 OBJ / 0 fallback, Dataset: graph stale, Material: 81 ok / 21 fallback color처럼 별도 축으로 노출한다.
장기적으로는 authoring_map → sync → render_scene.xml 재생성만으로는 XML-native editor가 완성되지 않는다. 최종 형태는 XML shape 선택 → transform/material/emitter patch → render_scene.xml 직접 수정 → xml_scene_index 재생성이다. 다만 이 전환은 위험하므로, 지금은 shape id와 marker 안정성을 유지하면서 PR5의 XML patch API로 천천히 넘어가는 것이 맞다.

리팩토링 단계

Phase작업목표
Phase 0현재 route dependency map을 유지하면서 더 이상 새 API/model logic을 +page.svelte에 추가하지 않는다.악화 방지.
Phase 1상태를 안 건드리는 순수 함수 추출: asset label/size/source_ref, envmap file conversion, geometry patch, readiness label.route script 1차 감량.
Phase 2API query를 service로 분리: load project, load graph, load render stats, load materialization audit, load rig.Model layer 복원.
Phase 2 status대부분 완료: 8개 service 파일이 생겼고 API 호출 책임이 route에서 빠졌다.Model layer는 8/10 수준으로 개선.
Phase 3ViewModel slice 생성: authoring, graph, render, cameraRig, assetCatalog, material, batch.상태 소유권을 domain별로 분리.
Phase 4route는 component composition만 담당하고, rail/tab 컴포넌트는 필요한 VM slice만 받도록 props를 줄인다.MVVM 구조 정착.
Phase 5render job traceability를 VM/service에 통합: authoring hash, rig id, XML hash, materialization status를 UI에 노출.렌더 디버깅 가능성 확보.
결론적으로 현재 UI는 서비스 추출 덕분에 Model 계층은 상당히 정상화됐다. 남은 핵심은 컴포넌트를 더 쪼개는 것보다 God Command 분해, state domain grouping, pageStore.svelte.ts 기반 ViewModel slice 도입이다. 기능 동작보다 유지보수성/회귀 방지에 직접 영향을 주는 단계다.

MapEditor3D MVVM 요소 분석

MapEditor3D.svelte는 현재 3D canvas View 역할만 하는 컴포넌트가 아니다. Three.js renderer lifecycle, interaction state machine, geometry/material preview mapping, mesh cache loading, frustum texture visualization까지 담당한다. 따라서 MVVM 기준으로는 View + ViewModel + Renderer Adapter + 일부 Model query가 섞인 상태다.
