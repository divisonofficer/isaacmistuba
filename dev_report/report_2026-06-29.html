Infinigen 생성 → import → nav graph → PBR 렌더

2026-06-29 Korean apartment floor-plan 2-stage importer robot-height nav graph PBR bake (roughness/normal/metallic)

요약

Infinigen 실내 생성물을 OpticalNav 데이터셋 파이프라인(에디터 · nav 그래프 · Mitsuba 렌더)에 흘려보내기 위한 end-to-end 작업을 정리한다. 네 단계로 나눈다: (1) 한국 아파트형 nav 맵을 만들기 위한 생성 옵션, (2) .blend → OpticalNav scene 임포트(2-stage), (3) 임포트 결과로 navigation node graph를 깔기 위한 처리, (4) 렌더 품질을 위한 PBR(roughness/metallic/normal) bake.

핵심 관점: Infinigen 기본 생성은 "거대한 단독주택 + 자연 terrain"에 가깝다. 로봇 내비게이션용으로는 단층 · 복도로 연결된 다실(多室) · 적당한 가구밀도 · 통창 같은 광학적으로 흥미로운 표면이 필요하다. 이를 seed 난수에 맡기지 않고 floor-plan prior + gin override로 강제하는 것이 1단계의 골자다.

1. Infinigen 생성 — 한국 아파트형 nav 맵 옵션

생성 래퍼는 scripts/infinigen_gen.py. Infinigen은 pip 설치돼 있어도 install 폴더에서 실행해야 하므로, 이 래퍼가 install dir/conda python으로 python -m infinigen_examples.generate_indoors를 호출한다(검증 대상: Infinigen 1.19.1). 기본은 --dry-run-safe(정확한 커맨드만 출력), --run 시 실제 실행(Blender+GPU 필요).

"아파트는 seed가 아니라 floor-plan prior"

한국 도시형 아파트 레이아웃은 난수 seed 하나로 나오지 않는다. seed는 한 config 안의 난수만 고정할 뿐이다. 그래서 8-digit seed AABBCCDD를 의미 있는 프리셋으로 디코딩한다(parse_seed):

자리의미값
AA유닛 타입59㎡ / 84㎡ / officetel
BB레이아웃 변형floor-plan 변종 선택
CC가구 밀도 → num_floatingmodel_house 8 · normal_lived_in 18 · family_home 28 · storage_heavy 40
DD카메라/조명 프로파일daytime_living / evening_warm / entrance_hallway / kitchen_to_living / robot_low_cam (현재 metadata에만 기록)

floor plan: kr_apt_84 (84㎡ 복도형, nav-friendly)

네비게이션에 가장 적합한 레이아웃으로 84㎡ 7실 복도형을 직접 author했다 — 거실 · 주방 · 식당 · 복도 · 침실×2 · 욕실. 특징:

  • 중앙 복도가 모든 방을 연결 — 복도 ↔ 각 방 문(door)으로 통행 가능한 그래프 위상(로봇 경로 생성에 유리).
  • open LDK — 거실↔식당↔주방은 문이 아니라 opens(벽을 쪼개는 문 없이 열린 연결)로 이어 큰 생활공간을 만든다.
  • 통창(panoramic window) — 거실 남측 외벽 창에 is_panoramic: 1을 줘 ~3m 바닥-천장 전면창을 강제. 랜덤 WindowFactory가 큰 창을 굴리길 기다리는 것보다 신뢰도가 높고, 유리/편광 렌더 테스트에 유용.
  • 방마다 외벽 창(window.00x) — 채광/환경광.

floor-plan 스키마는 rooms / doors / opens / interiors / windows 각각 name → {"shape": <shapely expr>, [is_panoramic]}. Infinigen Solver가 .json을 로드해 shape 문자열을 eval하므로(예: "shapely.box(0,0,5,5)") 좌표로 평면을 직접 그린다.

gin override (생성 옵션)

래퍼가 generate_indoors에 넘기는 검증된 override(build_command):

compose_indoors.terrain_enabled=False        # 실내 전용 (자연 terrain 끔)
Solver.floor_plan='<kr_apt_84.json>'          # 한국 아파트 평면 강제
compose_indoors.invisible_room_ceilings_enabled=True
compose_indoors.floating_objs_enabled=True
compose_indoors.num_floating=<density>         # 가구 밀도 (8~40)
compose_indoors.enable_collision_floating=True
compose_indoors.enable_collision_solved=True

2-stage 실행: layout(no_objects.gin + overhead.gin — 가구 없이 벽/cutter만 빠르게 검증) → full(object solve, 옵션 fast_solve.gin). 작은 평면 + 단순 위상(축 정렬 box)으로 solve 실패율을 낮춘다.

아직 코드 수정이 필요해 미연결: 랜덤 커튼/셔터 제거(WindowFactory가 @gin.configurable 아님), per-room material bias, 카메라 프로파일 실제 배치(seed의 카메라 자리는 metadata만).

사용법 (CLI)

# 커맨드만 출력 (dry-run, 기본): seed 디코딩 + floor_plan.json/kr_preset.json 기록 + 실행할 명령 표시
python scripts/infinigen_gen.py --seed 20003001 --stage full
# 실제 실행 (Blender+GPU 필요)
python scripts/infinigen_gen.py --seed 20003001 --stage full --run
# floor-plan 직접 지정 + gin override 추가
python scripts/infinigen_gen.py --seed 20003001 --floor-plan kr_apt_84 -p compose_indoors.num_floating=12 --run

주요 인자: --seed(AABBCCDD) · --stage layout|full · --fast(빠른 solve) · --floor-plan · -p/--override(raw gin) · --run. 산출물은 data/infinigen_generated/outputs/kr_<seed>/<stage>/ 아래에 floor_plan.json(방/문/창 geometry) + kr_preset.json(디코딩된 프리셋) + Infinigen 출력(blend 등). 임포트는 이 scene.blend를 받는다.

2. Import — .blend → OpticalNav scene (2-stage)

생성된 scene.blend(헤더 손상 시 scene.blend1 백업)을 OpticalNav scene으로 바꾸는 2단계. 원클릭 런처 apps/run_infinigen_import.sh <blend|dir>가 Stage 1+2+sync를 묶는다.

Stage 1 — bpy export (tools/infinigen/blender_export_scene.py, conda infinigen)

오브젝트(mesh "unit")별로 다음을 추출:

  • origin-local Y-up OBJ + GLB + 텍스처 + scene_manifest.json(분류·world bbox·transform·재질 PBR·조명·카메라·source_blend 경로).
  • 분류 _classify: structure(벽/바닥/천장) · door · window · furniture(Factory 이름 키워드 → semantic type).
  • 재질 PBR + optical_class 추출. _optical_class가 이름 우선(metallic 파라미터는 절차적이라 불신)으로 glass/mirror/metal(gold/steel/aluminum)/diffuse 분류 — 렌더 BSDF 선택의 근거.

export 함정과 대응(실전에서 막힌 것들):

증상원인대응
빈 OBJ (구조물 다수)Infinigen이 hide_viewport/hide_render로 숨김 → export·bake 거부_unhide로 일시 가시화
Mitsuba 로드 abortn-gon이 >1024 char OBJ 라인export_triangulated_mesh=True
invalid vertex normaldegenerate triangleexport_normals=False
black interior단면 BSDF 후면two-sided BSDF wrap

절차적 재질 bake: Infinigen 재질은 노드 그래프라 단순 색이 없다. Cycles DIFFUSE 패스를 per-object albedo atlas로 bake → MTL map_Kd로 연결(렌더가 실제 색을 픽업).

Stage 2 — converter (apps/import_infinigen_scene.py)

  • junk/미완성 제거: face 없는 OBJ(곡선·temp) 스킵(_obj_has_faces); 가구 ≥1인 "완성된 방"만 유지(_select_rooms — 원점에 쌓인 빈 더미 방 제거).
  • 좌표 정규화: 방을 양수 원점으로 translate + 바닥을 y=0에 안착(origin_offset = [dx, dy, dz]) — 에디터/렌더 좌표 일관성, nav 노드가 바닥에 깔리게.
  • 재질 바인딩(_material_binding, optical_class 기반): mirror→conductor, glass→dielectric/roughdielectric, metal→measured_polarized(hpbrdf aluminum/suj2/fake_gold) × baked albedo albedo_scale, diffuse→pplastic(편광 신호 + 텍스처). reflective(거울/유리)는 MTL의 baked Kd/map_Kd를 strip해 analytic strategy가 roughplastic으로 덮이지 않게.
  • 조명 power-conservation: 작은 강한 fixture는 far/어두운 곳에 firefly를 만든다 → 패널을 넓히고(LIGHT_SIZE_M) radiance를 면적 증가분만큼 나눠(_conserve_power) 총광량 보존·노이즈 감소.
  • 밴드 모드 렌더 옵션: 측정 pBRDF를 rgb(3밴드) / single(1밴드×albedo) / hybrid(무채색 금속 1밴드, 유색 3밴드)로 선택 — 메모리·속도 3× 절감(무채색 재질). Preview UI 셀렉터로 노출.

3. Navigation node graph 처리

임포트된 scene 위에 traversability grid → viewpoint node → edge를 까는데, Infinigen 기하 특성 때문에 추가 처리가 필요했다.

  • robot-height 통과 판정(object_blocks_at_height, walkable_surface.py): 물체의 바닥이 robot_height_m(기본 1.2m) 이상이면 로봇이 밑으로 지나가므로 막지 않는다 — 식탁·선반 아래 통행 가능. grid carve와 node-overlap 양쪽에 robot_height_m를 함께 전달한다.
  • 방 전체를 막는 오버블록 방지: Infinigen floor/ceiling은 room 크기 AABB를 가진 landmark라, 그대로 두면 방 전체 노드를 prune한다. find_object_overlapping_nodes가 navigation.blocks_navigation == False인 오브젝트를 건너뛰게 해 해결.
  • 얇은 가구는 walkable overlay: rug/carpet/mat/towel(키워드) 또는 world-AABB 높이 <5cm는 traversable로 두고 carve하지 않는다(_TRAVERSABLE_OVERLAY_*) — 깔개 위에 노드 구멍이 나 매번 수동으로 메우던 문제 제거.
  • 그래프 편집 히스토리 로깅(graph_edit_log.py): 사람이 자동 생성 그래프를 손볼 때(노드/엣지 추가·삭제, region 재샘플, overlap prune)를 scene별 append-only jsonl로 영속 기록 + "알고리즘 관점" 컨텍스트(삭제 노드의 clearance/manual, add-edge feasibility verdict, add-node의 기존 커버리지) — 추후 자동 path 생성 알고리즘 개선의 학습 신호.

4. 렌더 — PBR(roughness/metallic/normal) bake

문제: 임포트는 albedo만 bake했고 roughness/metallic은 스칼라 한 값뿐 — 절차적 입력은 못 읽어 디폴트(0.6/0.0)로 떨어져 공간 변화가 완전 소실됐다. per-texel roughness/normal을 렌더(roughplastic/pplastic의 texturable alpha, normalmap, 향후 principled)에서 쓰려면 맵 bake가 필요.

  • Stage 1 다중 패스 bake(--bake-pbr): _bake_pass로 일반화 — roughness/normal은 Cycles 직접 패스(ROUGHNESS/NORMAL), metallic은 직접 패스가 없어 EMIT 트릭(Principled Metallic→Emission로 임시 배선 후 EMIT bake, 슬롯별 복원). per-object atlas + MTL map_Pr/map_Pm/norm + manifest baked_*.
  • 렌더 소비: _extract_obj_mtl_material가 새 MTL 키를 읽어 roughness/metallic/normal_texture_ref 반환 → _append_extracted_bsdf_xml가 roughplastic/pplastic의 alpha를 스칼라 대신 텍스처(<texture name="alpha" raw>)로, normal은 기존 normalmap 어댑터로 emit.
  • --bake-only: 기존 scene을 Stage 1만 재bake(Stage 2 재임포트 안 함 → authoring map·수동편집 보존), 끝나면 staged 캐시 무효화로 다음 렌더부터 적용.
  • 상태 UI: Preview의 Sync Inspector에 "Infinigen PBR maps" 상태(roughness 베이크 N/total, normal/metallic 카운트) + "Bake PBR — copy cmd" 버튼(데몬이 Blender를 돌리지 않고, source_blend 기반 정확한 CLI 명령을 복사). 데몬 render-scene-stats가 import manifest의 baked_*를 읽어 상태를 계산.

비용은 패스 4×(albedo+roughness+normal+metallic)라 --bake-pbr 옵트인. 검증: 정상 베이크 오브젝트(blanket)에서 roughness std≈118(강한 공간변화), normal 정상, metallic EMIT 트릭이 비금속에 0/금속에 1을 정확히 산출. 측정 금속(measured pBRDF)은 자체 roughness가 있어 이 맵의 주 수혜는 pplastic/roughplastic 확산 표면.

참고: 일부 오브젝트(Balloon/Bed 류)는 albedo가 검정으로 bake되는데, 이는 이번 변경과 무관한 기존 내용 한계(셰이더가 DIFFUSE 패스로 안 잡힘)다.
metallic은 사실상 per-material 상수 — Infinigen은 metallic을 텍스처로 공간변조하지 않는다. 스칼라 분포가 scene 전반 87–94%가 0/1(대부분 0=비금속, 소수 1=금속; 나머지 0.375 등 비-binary 값도 per-material 상수)이고, 실제 bake한 metallic 맵은 4개 모두 std=0.00(완전 균일)이었다. 따라서 metallic 맵 bake는 균일 아틀라스만 생성해 per-material 스칼라 + optical_class(metal/비metal 분류)와 중복 — 사실상 낭비다. 진짜 per-texel 공간변화가 있는 건 roughness(std≈118)·normal 뿐. 기본값은 일단 그대로 두되(현재 --bake-pbr가 metallic까지 굽고 --no-bake-metallic로 제외), 추후 metallic을 기본 제외해 bake 패스를 4×→3×로 줄이는 것을 권장.

현재 상태 · 남은 일

  • 생성(kr_apt_84 floor-plan + seed 프리셋) · import(2-stage, 재질/조명/좌표) · nav graph(robot-height·overlay·edit log) · PBR bake(roughness/normal/metallic + 렌더 소비 + 상태 UI) 동작.
  • 남은 생성 옵션: WindowFactory 커튼/셔터 제거, per-room material bias, robot_low_cam 카메라 실제 배치(현재 metadata만).
  • metallic 맵 렌더 소비는 현재 scalar/binary 유지 — per-texel metallic은 principled/roughconductor-alpha 트랙에서 후속.
  • 측정 pBRDF 컬러는 production optix7에 measured_polarized_rgb 빌드(Phase 0) 후 완전 복원. analytic(pplastic/conductor/dielectric)은 이미 즉시 동작.

5. 측정 pBRDF가 "새까맣게" 보이는 현상 규명 — 버그 아님, 그리고 full-analytic 결정

infinigen_kr_20000221 vp_000039/h_240의 measured_full RGB 렌더에서 식기세척기(DishwasherFactory)가 순수 검정 실루엣으로 나와 "BRDF 매핑 실패냐"는 의심이 제기됨. 최소재현으로 분리한 결론은 버그 아님이다.

  • 관측: 식기세척기 영역이 재질·variant 무관하게 ~67% 정확히 0 (aluminum/white_rough_plastic, cuda_rgb/spectral/polarized 전부 동일, mean≈0.0083). NaN 없음, hpbrdf 채널 로드 정상, BSDF 20개 주입 정상. analytic은 같은 면을 dim하지만 비영(mean 0.02~0.086)으로 렌더.
  • 메쉬·BSDF는 정상: 노멀/UV가 전혀 없는 식기세척기 OBJ도 강한 직사광 최소재현에서 measured로 mean 0.39·검정 0%로 정상 렌더(sphere도 동일). → 메쉬·플러그인 문제 아님.
  • 진짜 원인 = analytic 과밝음 × 저조도: 동일 측면창광 통제 실험에서 analytic roughconductor("Al")가 measured aluminum pBRDF보다 ~4× 밝다(0.303 vs 0.076). roughconductor는 넓은 lobe·높은 Fresnel 반사율로 약한 창광도 긁어모으는 반면, 실제 measured는 반사율이 낮아 훨씬 어둡게 반사. 식기세척기는 거의 무조명 구석 → measured 신호가 바닥으로 붕괴하고 specular 반사 경로가 광원을 못 만나 Monte Carlo가 정확히 0을 반환.
  • 무관 변수 확인: alpha_sample 0.08↔0.5 결과 동일(=sampling lobe 폭 문제 아님), variant 무관, 재질 무관. 순수 반사 크기(밝기) 차이 + 조명 부족.
BSDF (sphere, 측면창광)meanexact-zero
measured aluminum (a=0.08 / 0.5)0.0760%
measured white_rough_plastic0.0520%
analytic roughconductor (a=0.2)0.3030%
analytic roughconductor (a=0.6)0.2820%

함의: measured가 물리적으로 더 정확하게(=더 어둡게) 반사하는데 analytic 근사가 과밝아서 저조도에서 극단적으로 갈렸을 뿐. measured vs analytic 비교는 대상에 충분한 조명을 준 조건에서만 유효하다.

결정: full-analytic 모드를 주력으로

위 결과 + 측정 pBRDF의 비용(밴드당 ~183 MB, GPU 메모리·로드)·저조도 취약성·Phase 0 빌드 의존성을 감안해, 당분간 full-analytic 모드(measured_scope=analytic_only)를 기본 렌더 경로로 삼는다.

  • 근거: pplastic(분극성 plastic) · dielectric(유리/투명) · conductor/roughconductor(금속) 세 analytic BSDF만으로 polarization + RGB + NIR을 모두 커버할 수 있다 — pplastic/conductor/dielectric은 모두 cuda_ad_spectral_polarized에서 Stokes를 내고, RGB·단일밴드(NIR proxy) 모두 즉시 동작.
  • 장점: 측정 데이터 로드/메모리 없음, 조명 강건성↑(저조도에서도 0 붕괴 없음), Phase 0(measured_polarized_rgb 빌드) 의존성 제거, 즉시 가용.
  • 측정 pBRDF는 선택적/연구용으로 보존: measured_scope=measured_full/analytic_priority 경로는 유지하되, 데이터셋 기본 생성은 analytic로 간다. 측정 비교가 필요하면 대상에 충분한 조명을 준 조건에서만.
  • 후속 검토(별개): hpbrdf aluminum의 절대 반사 스케일 vs analytic Al reflectance 정량 매칭 — "측정 금속이 너무 어둡다"가 데이터 스케일 이슈인지 확인.
