Polarization Camera 렌더 파이프라인 구현 상태

chairtest scene에 polarization camera를 선언하고 기존 UI preview 렌더 경로로 돌렸을 때, 결과가 "gray인 듯, 색감이 있는 듯"한 일반 이미지처럼 보이는 원인을 분석한다.

결론: Stokes 렌더 자체는 수행된다. 문제는 UI 기본 preview가 Stokes 원본에서 뽑은 RGB preview 한 장만 요청·표시해서, 사용자가 DoP/AoLP/S1/S2 같은 편광 정보를 직접 확인할 수 없다는 점이다.

오늘의 결론

실제 렌더
Stokes
cuda_ad_spectral_polarized + <integrator type="stokes">로 15채널 텐서가 생성됐다.
UI 요청
1장
hot camera preview는 polar_rgb_preview 단일 modality만 요청했다.
숨은 데이터
NPZ
stokes_data.npz에는 RGB/S0/S1/S2/S3/DoP/AoLP가 들어 있지만 UI에서 읽지 않는다.
핵심 문제
UX
preview가 polarization map처럼 라벨링되지만 실제로는 Stokes render의 RGB tonemap이다.
요약: "polarization cam이 동작하지 않는다"보다는 "polarization cam의 기본 결과가 해석 가능한 편광 산출물로 노출되지 않는다"가 더 정확하다. 렌더 backend는 Stokes 텐서를 만들고 있지만, UI/manifest/export 계층이 그 의미를 충분히 드러내지 못한다.

chairtest 관찰 기록

확인한 job은 opticalnav-shared_office_floor_001_chairtest-template-probe_1781665715059-h0-polar_rgb_preview 이다. manifest 기준 요청 modality는 polar_rgb_preview 하나이며, camera id는 polar_cam이다.

항목값해석
variant cuda_ad_spectral_polarized 편광 variant로 렌더가 수행됐다.
integrator stokes + nested direct 출력은 Stokes 기반 다채널 텐서다.
stokes shape [360, 480, 15] RGB 3채널 + S0/S1/S2/S3 각 3채널 구조로 해석된다.
saved files polar_rgb_preview.png, stokes_data.npz S1/S2/DoP/AoLP preview PNG는 요청되지 않아 생성되지 않았다.
material mode original_scene fallback scene이 아니라 원본 scene의 polarized-compatible BSDF 조합으로 렌더됐다.
polar signal s1 p99.5≈0.0209, s2 p99.5≈0.00919, masked DoP p99≈0.482 편광 신호는 존재한다. 단지 preview 이미지 한 장으로는 잘 보이지 않는다.

현재 파이프라인

UI camera rig polar_camera └─ canonical modalities: polar_rgb_preview, dop, aolp, s1, s2 Preview tab hot camera render active sensor 선택 └─ sensorRenderModality(polarization) = polar_rgb_preview └─ request body modalities = [polar_rgb_preview] render_daemon / multimodal.py _needs_polar() == true ├─ stage scene_polar.xml │ integrator = stokes │ nested integrator = direct 또는 volpath ├─ render with cuda_ad_spectral_polarized ├─ extract_stokes_channels(image) │ rgb = image[:, :, 0:3] │ s0/s1/s2/s3 = later channel groups └─ save_polarization_products() ├─ always: stokes_data.npz └─ requested only: polar_rgb_preview.png
핵심: backend는 polarization branch에 들어간다. 하지만 preview UI는 canonical polar modality 전체가 아니라 polar_rgb_preview 하나만 요청한다. 그래서 사용자가 보는 것은 "편광 카메라의 RGB 미리보기"이지 "편광 물리량 시각화"가 아니다.

원인 ① — Hot camera preview가 polar_rgb_preview만 요청한다

dataset UI의 sensorRenderModality()는 authoring map의 modality="polarization"을 polar_rgb_preview로 변환한다. 이후 hot camera 렌더 body는 modalities: [activeRenderModality] 형태로 전송된다.

단계현재 동작결과
sensor 선택 polarization sensor 선택 UI 내부 active render modality가 polar_rgb_preview가 된다.
preview submit modalities: ["polar_rgb_preview"] dop, aolp, s1, s2는 생성 대상에서 빠진다.
drawer display job의 대표 image URL 한 장 표시 colorbar, Stokes 통계, raw channel 목록 없이 일반 이미지처럼 보인다.

원인 ② — polar_rgb_preview는 편광 map이 아니다

save_polarization_products()는 Stokes 렌더 결과에서 rgb = image[:, :, 0:3]를 분리하고, _rgb_preview_array()로 percentile tone mapping을 적용해 polar_rgb_preview.png를 저장한다. 즉 이 이미지는 "Stokes render에서 같이 나온 RGB radiance preview"이다.

혼동 지점: 파일명이 polar_rgb_preview라서 polar branch의 결과라는 사실은 맞지만, 이미지 내용이 DoP/AoLP/S1/S2를 encoding한 것은 아니다. 그래서 회색 RGB 이미지처럼 보이는 것이 정상에 가깝다.
산출물의미사람이 봤을 때
polar_rgb_preview.png Stokes 렌더의 RGB 채널 tonemap 일반 RGB/gray preview처럼 보임
s1_bwr_colorbar.png luminance-weighted S1 signed field blue-white-red signed map
s2_bwr_colorbar.png luminance-weighted S2 signed field blue-white-red signed map
dop_red_black_colorbar.png Degree of Polarization, 0..1 polarization strength map
aolp_rainbow_colorbar.png Angle of Linear Polarization, 0..180 deg orientation hue map

원인 ③ — raw polarization 데이터는 저장되지만 UI/복사 계층 노출이 약하다

  • stokes_data.npz는 항상 저장된다. 여기에는 rgb, s0, s1, s2, s3, dop, aolp, mask가 들어 있다.
  • 그러나 job drawer는 대표 PNG 한 장과 raw log만 보여준다. s1_scale_abs_p995, finite_ratio, fallback_used, stokes_shape 같은 진단값은 화면에 드러나지 않는다.
  • 데몬의 일부 mapping은 dop.exr, aolp.exr, s1.exr, s2.exr를 기대하지만, 현재 저장 함수는 colorbar PNG와 stokes_data.npz 중심이다. raw scalar artifact 계약이 아직 정리되지 않았다.
  • OpticalNav consolidated observation tree로 복사되는 것도 PNG 중심이다. stokes_data.npz가 sensor output의 first-class artifact로 보이지 않는다.
결과: backend에는 polarization 정보가 있는데, UI에서는 "어떤 Stokes 값이 나왔는지"가 보이지 않는다. 따라서 사용자는 preview 한 장만 보고 이게 polarization인지 RGB인지 판단해야 하는 상태다.

원인 ④ — gray인 듯 색감 있는 듯 보이는 이유

요인설명
RGB preview 자체 polar_rgb_preview는 DoP/AoLP map이 아니라 RGB radiance preview다. 장면 조명과 재질 색이 약하면 회색에 가깝게 보인다.
단일 wavelength measured pBRDF chairtest의 scene_polar.xml에는 HPBRDF channel 중 542.pbrdf가 여러 measured material에 쓰인다. 단일 녹색 파장 기반이면 RGB 색상 다양성이 제한된다.
ambient_room 조명 이번 job은 assist light 없이 illumination_tag=ambient_room이다. 편광 cue가 강하게 드러나는 active polarized illumination setup이 아니다.
S1/S2가 preview에 직접 encoding되지 않음 편광 차이는 s1/s2/dop/aolp에 존재하지만, 화면에 표시된 PNG에는 그 차이가 색상으로 들어가지 않는다.

권장 방향

UI 기본값
polar camera는 full polar set 요청

preview probe에서도 polar_rgb_preview,dop,aolp,s1,s2를 함께 요청한다. 시간이 부담되면 같은 Stokes pass에서 파생되므로 추가 렌더 비용은 거의 없다.

표시 방식
RGB preview와 polarization map 분리

polar_rgb_preview는 "Stokes RGB preview"로 라벨링하고, 대표 썸네일은 DoP 또는 AoLP로 선택 가능하게 한다.

artifact 계약
Stokes raw를 first-class로 승격

stokes_data.npz를 manifest/export/observation scan에서 명시하고, scalar EXR 저장 여부를 결정한다.

실행 우선순위: 먼저 UI 요청을 full polar set으로 바꾸고, job drawer에서 DoP/AoLP/S1/S2 thumbnail을 보여준다. 물리 모델 자체를 고치기 전에 산출물의 의미를 명확히 보여주는 것이 먼저다.

구현 태스크 초안

순서태스크위치완료 조건

5 물리 camera model 구분 문서 + modality naming stokes 산출물과 analyzer camera intensity(I0/I45/I90/I135)를 명확히 구분

완료 기준

  • polar camera hot preview를 한 번 누르면 polar_rgb_preview.png만이 아니라 dop_red_black_colorbar.png, aolp_rainbow_colorbar.png, s1_bwr_colorbar.png, s2_bwr_colorbar.png가 같이 생성된다.
  • UI에서 대표 preview가 "Stokes RGB preview"인지 "DoP"인지 "AoLP"인지 명확하게 표시된다.
  • manifest에서 variant=cuda_ad_spectral_polarized, stokes_shape, material_mode, fallback_used, s1/s2 scale를 확인할 수 있다.
  • export된 dataset에서 polarization raw data의 위치가 명확하다. 최소 기준은 stokes_data.npz를 sensor artifact로 보존하는 것이다.
  • 문서에서는 polar_rgb_preview를 편광 물리량 이미지로 부르지 않는다. 편광 물리량은 DoP/AoLP/S1/S2/Stokes로 지칭한다.
최종 판단: 현재 구현은 Stokes 렌더 기반을 이미 갖고 있다. 다만 UI preview의 기본 선택과 artifact 계약이 RGB preview 중심이라 편광 데이터셋으로서의 의미가 흐려진다. 다음 개선은 렌더러보다 UI/manifest/export의 polarization product surface를 정리하는 쪽이다.
