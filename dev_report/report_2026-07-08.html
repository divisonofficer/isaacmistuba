Infinigen degenerate-UV 근본원인 규명 & PBR bake 파이프라인 수정

scene: infinigen_kr_20260625 tools/infinigen/blender_export_scene.py 2026-07-08

요약

Infinigen import 오브젝트가 albedo/roughness/metallic 을 잃고 렌더되던 문제(대표 사례: 침대 프레임의 편광·roughness 소실)의 진짜 근본원인을 찾았다. Geometry-Nodes로 생성된 spawn_asset 오브젝트의 UVMap이 전부 (0,0) 한 점에 뭉친 degenerate(zero-area) UV였고, 이 위에 bake하면 아틀라스 전체가 1 texel로 붕괴되어 새까만 텍스처가 나온다.

어제(07-07)의 "procedural roughness가 bake 시 collapse한다"는 진단은 오판이었다. 모든 실험이 이 degenerate UV 위에서 수행되어 교란(confounded)됐던 것 — UV만 정상화하면 Cycles ROUGHNESS pass가 실제 per-texel 값을 정확히 구워낸다.

수정 3종(① degenerate UV 감지·재투영 ② bake 중 OOM 방지 isolation ③ 고폴리 게이트 flag)을 적용하고, 영향받은 28개 render-relevant 오브젝트를 재-bake했다. 침대 albedo 0.000→0.159, 선반소품·화분 등 0.5–1.5M 폴리 장식물 20종이 모두 실제 아틀라스를 갖게 됐다.

1. 증상

vp_000030 뷰포인트에서 침대 나무 프레임의 편광 신호가 거의 0, 재질 뷰어에는 roughness≈0.6으로 뜨는데 렌더된 텍스처는 나오지 않았다. 동료들은 "편광을 지원하지 않는 material plugin이 붙은 것 아니냐"고 물었으나, BSDF plugin 문제가 아니라 애초에 이 오브젝트에 텍스처가 실려있지 않았다(아틀라스가 새까맸다).

2. 근본원인 = degenerate UV

침대 오브젝트를 뜯어보니 UVMap 레이어는 존재하는데 73,932개 loop의 UV가 전부 정확히 (0,0)이었다. UV 면적이 0이므로 어떤 bake(albedo/roughness/metallic)든 아틀라스의 단 1 texel에만 래스터화되어 나머지는 검게 남는다. Infinigen 절차 재질은 object-space(Generated/Object) 좌표로 shading하므로 UV가 필요 없어, GN 파이프라인이 placeholder UVMap을 만들되 좌표를 채우지 않은 채 남긴 것 — Infinigen 자체 렌더에는 무해하지만, 우리처럼 텍스처 아틀라스로 bake·OBJ export하는 소비 경로에서만 터지는 버그다.

3. 어제 진단이 틀렸던 이유

07-07에는 "procedural roughness(Noise→FloatCurve)가 GN 메쉬에서 bake 시 0으로 collapse하며, 좌표(Generated/Object/UV/Position)를 주입해도 복원 안 된다"고 결론냈다. 그러나 그 실험들은 전부 degenerate UV 위에서 bake한 것이라, 좌표를 무엇으로 바꾸든 UV 면적이 0이니 당연히 아틀라스가 검게 나왔던 것이다(교란된 실험). UV를 정상화하자:

passdegenerate UV정상 UV (Smart-Project)
albedomean 0.000mean 0.159 · max 0.490 (실제 나무색)
roughnessmean 0.000mean 0.144 (spatial pass 정상 작동, 상수 fallback 미사용)
metallic0.0000.000 (나무 → metallic=0, 정상)

즉 procedural은 붕괴하지 않았다. 결함은 오로지 UV였다.

4. 코드 수정 3종 blender_export_scene.py

#수정내용
①_uv_is_degenerate + _ensure_uv 기존 _ensure_uv는 UV가 없을 때만 Smart-Project 했다. 이제 active UV의 bbox span이 <1e-4인 degenerate UV도 감지해서 placeholder를 버리고 새로 투영한다. OBJ export·bake가 동일한 정상 UV를 공유.
②_render_isolate(obj) 2.8GB blend의 ~14M 폴리 전 씬을 Cycles가 bake마다 sync → 11GB WSL 박스에서 OOM kill(RSS 9.9GB). bake는 direct/indirect 조명 OFF라 다른 지오메트리가 기여하지 않으므로, bake 동안 대상 외 오브젝트를 hide_render 처리 → 메모리를 대상 하나로 제한(무손실).
③--max-poly N (기본 120000) 고폴리 diffuse 장식물(0.5–1.5M 폴리)이 하드코딩 폴리 게이트에 조용히 skip되고 있었다. isolation으로 메모리가 잡히니 2,000,000으로 올려 이들도 bake(검증: 528k 선반소품 정상, 메모리 baseline 유지).

부수적으로 손상된 manifest를 건드리지 않고 타깃 재-bake하는 --only-degenerate(zero-area UV 오브젝트 자동 선택) + --merge(blender_name 기준 splice, 기존 id 재사용해 파일 제자리 덮어쓰기) 플래그를 추가했다.

실행: $INFINIGEN_PYTHON tools/infinigen/_run_bpy.py <scene.blend> tools/infinigen/blender_export_scene.py -- --out out/infinigen_imports/kr_20260625 --only-degenerate --merge --bake --bake-pbr --max-poly 2000000 --bake-res 512

7. GLB 소비로 전환해야 하나? — 고찰

"앞으로 렌더가 GLB를 소비해야 UV를 제대로 읽는다"는 방향에 대해 검증했다. 재-export된 bed GLB를 직접 디코딩한 결과:

GLB가 담는 것GLB가 못 담는 것
mesh (POSITION/NORMAL)텍스처: images=0, textures=0
TEXCOORD_0 UV [0.009–0.991] (수정 반영됨)baseColorFactor=None (재질은 이름만)
node transformInfinigen procedural node 그래프
핵심: Infinigen procedural 재질(Noise→FloatCurve→Principled)은 glTF export 시 빈 PBR로 flatten된다 — GLB에는 albedo/roughness 텍스처가 하나도 안 들어간다. 따라서 GLB만으로는 재질이 flat하게 렌더되고, 정확한 per-texel 재질은 여전히 bake된 아틀라스에서 와야 한다.

또한 이번 37개는 .blend의 UV 자체가 degenerate였으므로 GLB로 뽑아도 동일하게 (0,0)이 나왔을 것이다 — GLB가 UV를 "제대로 읽는" 게 아니라, _ensure_uv 수정이 degenerate를 고쳐 OBJ·GLB 둘 다 정상화한 것이다. 결론:

  • 올바른 아키텍처 = GLB(지오메트리+UV+transform 견고성) + bake 아틀라스(재질). daemon에 배선 존재(_split_glb_shapes_cached → authoring material_id → 아틀라스), ROBOMITUBA_INFINIGEN_USE_GLB=1로 활성화.
  • GLB 전환은 OBJ의 vt=0 barycentric 취약성을 없애는 견고성 이득이며, bake 파이프라인을 대체하지 않고 함께 간다.
  • 어느 경로든 degenerate-UV 수정이 선행돼야 한다.
